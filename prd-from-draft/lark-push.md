# 飞书推送手册

PRD 推到飞书的完整流程与踩坑记录。**推送是长文档里最容易出问题的一步**，因为它同时涉及网络、服务端转换与附件三件事，而这三件事**都会静默失败**——不会报错，只会少东西。所以这一步的重点不是「怎么推」，而是**怎么确认推对了**。

---

## 1. 首次创建 vs 后续更新

| 场景 | 命令 |
|------|------|
| 文档不存在 | `lark-cli docs +create --doc-format markdown --content @./<cwd 下相对路径>` |
| 文档已存在，整篇替换 | `lark-cli docs +update --doc <token> --command overwrite --doc-format markdown --content @./<相对路径>` |

🔴 **`@file` 只接受 cwd 下的相对路径**，绝对路径会报 `unsafe file path`——但**文件可能已经上传并生成了孤儿块**。用绝对路径试过一次后，务必回读确认有没有留下重复附着。

🔴 **重推不要用 `+create`**——会建出重复文档，旧的那份还留在云空间。已有文档一律 `overwrite`。

`overwrite` 是整篇替换，Lark 侧有历史版本可回滚（`+history-list` / `+history-revert`，注意 revert 用的是 `history_version_id` 而不是 `revision_id`）。

## 2. 推送前：三件必做的小事

> 本节适用于 `--doc-format markdown` 这条路线（本地 markdown → 服务端转换）。技能内的 `md-to-lark.js` 走的是 block JSON 路线，内容以 `text_run` 提交，不存在 `<` 被当 HTML 解析的问题——**两条路线的转义要求不同，不要混用**。

### 2.1 转义裸 `<`

**裸 `<` 会被 Lark 当 HTML 解析，内容直接吞掉。** 行内的 `<` 要写成 `\<`，渲染后显示为 `&lt;`。**跳过代码围栏**——``` 块里的 `<br/>` 不用转。

```python
fence = False
for line in text.split('\n'):
    if line.lstrip().startswith('```'):
        fence = not fence; out.append(line); continue
    if not fence:
        line = re.sub(r'(?<!\\)<', r'\\<', line)   # 不重复转义已转过的
    out.append(line)
```

⚠️ **最危险的形态是 `<` 出现在表格单元格开头**（`| < 50 | 低 |`），行中（`**< 3**`）也建议一并转，成本很低。推完用 `grep -c '&lt;'` 和 `grep -c '\\<'` 双向确认：前者应有值，后者应为 0。

### 2.2 表格三层列数校验

**表头 / 分隔行 / 正文行三层列数必须一致**，否则整张表在飞书里降级成纯文本。这是自己手写表格时最高频的失误。

```python
# 逐张表比对三层列数；表头、'|---|'、每一行都要数
# 也检查「表格单元格里出现字面竖线」——写版本记录时最容易犯
```

### 2.3 确认页头版本号

改完 PRD 记得同步页头 `**版本：Vx.y**` 与 §7 版本记录。**页头的版本号是唯一能从飞书侧一眼判断「推的是哪一版」的信号**，用它可以确认推送是否落地（见 §3.1）。

## 3. 推送与验收

### 3.1 `+update` 报 timeout ≠ 没写进去

**实测：连续 4 次返回 `"ok": false, "subtype": "timeout"`，回读发现正文已经是新版本**（revision 从 604 走到 668、页头已是新版本）。整篇 overwrite 大概率**写入成功、只是响应超时**。

所以：**超时后先 `+fetch` 回读确认，不要无脑重推**——重推虽然幂等，但每次都会清空附件，白跑一轮挂附件的流程。

### 3.2 验收信号：标题结构逐条比对

**不要用正文长度、也不要看单次 fetch 的形态判断成功与否。**

```python
# 本地：^#{2,6} 取出标题文本
# 飞书：<h[2-6]>(.*?)</h[2-6]> 取出标题文本
#       标题内可能含 <b>/<code> 等行内标签 → 先取到闭标签、再剥标签
# 两边都去掉空白与 * 后，作为多重集比对：missing 与 extra 都应为空
```

⚠️ **层级别写死 `2,5`**：文档用几级标题就匹配几级。此前一直写 `^#{2,5}` / `<h[2-5]>`，是因为全文从没用过六级标题；**一旦正文出现 `######`，写死 5 会让这些标题在两侧同时缺席、比对恒过**——比对结果全绿，实际漏掉了整批小节，是最隐蔽的一类假通过。

**六级标题可用**（2026-09-29 用临时文档实测）：`######` 导入后是**独立的 `<h6>` 块**、出现在 `+fetch --scope outline` 的大纲里、不会把后面的表格并进上一段。附件/画板数那套验收不受影响。

### 3.3 🔴 `+fetch` 返回的正文可能不完整

同一份文档，推完**等 4 秒**读只有 79 个标题、正文止于中途且开头多出一段重复块；**等 10 秒**再读就是完整的 136 个标题、无重复。

**当时第一反应是「overwrite 把文档写坏了」，是误判**——那是读取端的假象。**宁可多等几秒再读**，并始终以「结构比对」为准。

## 4. Mermaid → 画板

### 4.1 失败是随机的

同一份文档连续推多次，转成的画板数会跑出 2 / 4 / 5 / 6 / 7 / 8。**这是转换服务的偶发失败，重试即可。**

🔴 **不要从单次观测总结内容规律。** 曾看到「每轮都是某一张图失败」，据此怀疑那张图的语法（链式边）有问题——**连采 3 个样本后，失败的小节每次都不同**，纯随机分布。

想确认某张图到底能不能转，可以取历史版本自证：

```bash
lark-cli docs +fetch --doc <token> --revision-id <n>   # 回看某个 revision 的样子
```

### 4.1.1 🔴 `degrade_code=2107` 不是内容诊断——先做单变量对照

定点补图时，失败会带出两条警告：

```
degrade_code=2107,msg=Whiteboard content parse failed. Check the whiteboard content format
degrade_code=1003,msg=Instruction produced empty content after transform...
```

**`2107` 看起来在指责内容格式，实际上随机失败也会带出同一条**，两条警告无法区分「内容真的有问题」和「服务偶发失败」。

⚠️ **踩过的坑**：某次补图，两张图报 `2107`；恰好一张是全篇唯一含 `≥` 的图、另一张是唯一用 `-->|"text"|` 的图，于是**断言是这两个语法导致的**，改完就成功了，还把「confirmed」写进了汇报。**结论是错的**——把失败的那份内容**原样**再插一次（一字未改）直接成功；`≥` 版本重试第 3 次也成功。真相是随机失败。

**两条通用教训**：

1. **判内容是否有问题，唯一可靠的做法是「同一份内容重试 ≥ 3 次」**——不要看警告文案，也不要拿别的图作对照。
2. **「改一下就成功了」是最强的假因果**——在随机失败的世界里，任何改动都会显得有效。**在断言某个字符 / 语法是原因之前，必须先做一次单变量对照（同内容重试）。** 否则会把无关的改动写进 PRD，制造一个凭空多出来的「约束」。

> 顺带一个反例留档：`-- "text" -->`（短横线标签）与 `-->|"text"|`（竖线标签）、`≥`、全角括号、链式边——**目前都能正常转换**，不要预防性地把它们改写掉。

### 4.1.2 数画板 / 数附件：注意标签带属性

```bash
grep -o '<whiteboard' | wc -l      # 画板：开标签，这样数是对的
grep -c '<figure'                  # 附件：必须用 '<figure'，不能用 '<figure>'
```

⚠️ **附件块是 `<figure view-type="Card"><source name="..." size="..." token="..."/></figure>`**——标签**带属性**，用 `count('<figure>')` 会得 **0**，看起来像「附件全丢了」，实际一个没少。**所有计数一律匹配开标签前缀，不要匹配完整的空标签。**

### 4.2 失败的图会连代码块一起消失

转换失败时，**该小节只剩标题**——既无画板也无代码块残留，静默丢弃。所以 `+whiteboard-update` 用不上：**它只能改已存在的画板**。

### 4.3 ⭐ 定点补图，不要整篇重推

既然失败的图会定点缺失，就**定点补回去**——把「N 张全对的抽奖」变成「逐张修」，而且不惊动已转好的图。

```bash
# 1. 拿失败小节标题的 block id
lark-cli docs +fetch --doc <token> --detail with-ids    # 找到 <h4 id="doxcnXXXX">3.2.4 标题</h4>

# 2. 把该小节的 mermaid 源码写成文件，插到标题后面
lark-cli docs +update --doc <token> --command block_insert_after \
  --block-id "doxcnXXXX" --doc-format markdown --content @./_ins.md

# 3. 返回里 block_type 为 "whiteboard" 即转换成功
```

**服务端会把插入的 ```mermaid 块直接转成画板。**

⚠️ 插入调用**可能返回 `ok:false` 但其实已经插进去了**（反之也可能真的没插）。补完必须回读、数一遍该小节的画板数，确认**没有重复**。

⚠️ `block_insert_after` **不会清空附件**（与 `overwrite` 不同）——这是定点补图相对整篇重推的又一个好处。

### 4.4 其它已知禁忌

- **`loop` 标签里的全角括号会让整张图被静默丢弃**。消息标签、状态标签、节点标签里的全角括号目前都能过，只有 `loop` 不行。

## 5. 附件

- 用 `lark-cli docs +media-insert --doc <token> --type file --file ./<相对路径>`，文件块**追加在文档末尾**，显示为可下载的 File Card（HTML 不能在线预览，只能下载后打开）。
- 🔴 **`overwrite` 会清空全部附件**——每次整篇重推后都要重新挂一遍。**定点补图不会**，这也是优先定点编辑的理由之一。
- ⚠️ **每次 `+media-insert` 都无条件追加，不查重**——不要放进 `for` 循环里重复调、也不要「怕没成功」再补一次，否则会留下重复块。真重复了用 `+update --command block_delete --block-id "<id1>,<id2>"` 清掉（需要 `+fetch --detail with-ids` 拿块 id）。
- 成功的判定看 `"ok": true`；`+fetch` 的正文**不渲染附件块**，校验要抓 `<figure><source name="..." token="..."/></figure>`（token 是文件 token，不是块 id）。

## 6. 🔴 服务降级 vs 内容问题：先判别再动手

**在写接口故障的窗口里盲目重试几十轮 overwrite，是这一节最想避免的事**——每轮耗时且结果随机，还会把已转好的画板反复清掉。

一条命令就能分清：

| 探测 | 类型 | 健康 | 降级 |
|------|------|------|------|
| `+fetch` | 读 | 正常，约 1~2 秒 | — |
| `+history-list` / `+update` | 写 | 正常 | **每次都 `INTERNAL TIMEOUT`** |

**读正常 + 写全超时 = 服务端写路径降级**，不是文档内容的问题。此时正确动作是**停下等待**，而不是继续抽奖。

## 7. 常见误区速查

| 想法 | 实际 |
|------|------|
| 「推完看返回的 `ok` 就够了」 | 读操作要看内容；写操作超时也可能已成功。**验收一律回读。** |
| 「画板少了，肯定是那张图写得不对」 | 随机失败。**连采 3 个样本再下结论。** |
| 「`2107` 报内容解析失败，那就是图写错了」 | 随机失败也报这一条。**同内容重试 ≥ 3 次**才是判据。 |
| 「改完就成功了，果然是这里的问题」 | 随机失败下的假因果。**先同内容重试一次**，再谈改动。 |
| 「fetch 读出来不对，文档坏了」 | 可能是读取不完整。**等久一点再读，以结构比对为准。** |
| 「少一张图，整篇重推一次吧」 | 会清空附件、还会把其余 N-1 张重新摇一次。**定点补图。** |
| 「附件数出来是 0，全丢了」 | 标签带属性，是你数错了。**匹配 `<figure` 而不是 `<figure>`。** |
| 「再推一次保险」 | 重推幂等但会清空附件；**没有新改动就不要推**。 |
