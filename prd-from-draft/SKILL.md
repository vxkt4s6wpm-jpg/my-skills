# prd-from-draft

描述 / 图片 / 原型 → 草图原型 → 需求 PRD → 飞书。

## 核心原则：三道确认门禁

每个阶段的产出必须经用户**明确确认**，才能进入下一阶段。

| 门禁 | 产出 | 放行信号（用户原话） |
|------|------|----------------------|
| Gate 1 | 草图原型 HTML | "原型可以" / "没问题" / "继续" |
| Gate 2 | 需求 PRD | "PRD 可以" / "确认" / "推送吧" |
| Gate 3 | 飞书文档 | "推送" / "上传" |

**违反形式即违反精神**，以下行为均视为违规：

- 用户只给了描述，就一路做到飞书文档
- 原型还没确认就先生成 PRD「省时间」
- 以「原型很简单不用确认」为由跳过 Gate 1
- 把 PRD 生成当作原型的确认

## 核心原则：同一轮只改一样

**原型与 PRD 不要在同一次改动里一起改**——先改一样，确认后再改另一样。**判断不出这一轮该改原型还是该改 PRD 时，先问一句**（一句话问清，不要列一堆选项）；只有用户明确说「两边都改」才一起改。

两个文件一起改的实际代价：

- **用户无法逐样评审**，只能整体接受或整体回滚——2026-09-29 的一次改动就是这样被整体回滚掉的，**两边的返工一起作废**；
- **回滚面翻倍**：要同时精确还原两份文件，出错面变大（那次靠「字符数必须回到改动前的值」作断言才确认还原干净）；
- 两边的改动互相遮挡，中间过程也无法单独保留。

> 改动落点可以先从用户的措辞找线索——偏规格的措辞（「补充…取值逻辑」「…的阈值是什么」）指 PRD，偏现象的措辞（「…不对」「…不是横条」「…溢出了」）指原型。**线索不足就问**，不要靠猜。

## 执行流程

### Phase 1：生成草图原型

**触发**：用户给出需求描述、图片路径、已有原型文件，或说"生成原型"。

**输入识别**：

| 输入 | 处理方式 |
|------|----------|
| 文字描述 | 按描述推断页面结构、字段、交互 |
| 图片 / 截图 / 手绘 | 视觉解析布局、字段、交互，重建为可运行 HTML |
| 已有 HTML 原型 | 读取源码，增量改造，输出新文件（不覆盖原文件） |
| 描述 + 图片 | 图片定视觉与布局，描述定字段规则与业务逻辑 |

**步骤**：

1. 确定需求名称、应用端（H5 端 / Web 端 / 双端）；未指定则询问
2. 读取本技能目录下的 `prototype-template.html` 骨架与 `DESIGN.md` 规范
3. 输出 `[需求名称]-原型.html` 到 `<工作区>/UI/prd/`
4. 按下方「原型自检清单」自检，再截图给用户

**骨架已内置的能力，直接复用，不要另起一套样式**（此处只列「有什么」，各项规格一律查 `DESIGN.md`）：

- **设计 token**：仅亮色一套（无 `[data-theme]` 分支、无主题切换）。全量 `--semi-*` 语义色 + `--brand-*` 品牌层与渐变 → §2
- **图标库**：55 个内联 SVG symbol，单一来源 Arco 官方 outline（48 画布 / 线宽恒 4 / 零自绘）。用法 `<svg class="icon"><use href="#i-search"/></svg>`；**一图一义**是硬要求，新增图标先取 Arco 实源（取法与映射表见骨架文末注释）→ §5.4
- **组件库**：按钮 / 输入 / 筛选栏 / 卡片 / 指标卡 / 标签 / 表格+工具栏+分页 / 描述列表 / 时间轴 / 开关 / 提示条 / 空态 / 骨架屏 / 抽屉 / 弹窗 / 二次确认 / 步骤条 / 分组标题 / 底部标签栏 / 登录页
- **外壳**：H5 端 `.phone`（平铺页加 `.is-flat`）、Web 端 `.web-layout`（可折叠侧边栏）、登录页 `.login-page`（默认隐藏）。**外壳决定几何形态**——同一份标记换外壳即换观感，不要手写 `style` 覆盖 → §5.8 / §5.9
- **交互工具**：`openDrawer()` / `openModal(id)` / `askConfirm(标题, 文案, 回调)` / `toast(文案, type)` / `toggleCollapse()`

**原型必须表达的内容**：

- 页面布局与入口位置
- 筛选条件、列表字段、行操作
- 表单字段（类型、必填标识、校验提示）
- 状态标签、空状态、加载态、错误态
- 关键交互（弹窗、二次确认、字段联动）

### Phase 2：确认原型（Gate 1）

1. 用 Chrome headless 截图，把截图给用户看
2. 主动列出原型中**推断/假设**的点，请用户逐条确认
3. 用户提修改 → 改 HTML → 重新截图 → 重复
4. 用户明确确认后，才进入 Phase 3

### Phase 3：生成需求 PRD

**步骤**：

1. 读取 `general-prd-template.md`
2. 以**已确认的原型**为唯一事实来源，反推字段定义、业务规则、权限点
3. 业务流程生成 Mermaid 图（flowchart / sequenceDiagram / stateDiagram）
4. 使用系统当前日期
5. 输出 `YYYY-MM-DD-[需求名称]-prd.md`（与原型同目录）
6. PRD 头部标注对应的原型文件路径

### Phase 4：确认 PRD（Gate 2）

1. 摘要列出 PRD 覆盖的页面数、字段数、待确认项
2. 用户明确确认后，进入 Phase 5

### Phase 5：推送飞书（Gate 3）

**动手前先读 `lark-push.md`**——长文档推送的坑几乎全在「静默失败」上：不报错，只少东西。

**步骤**：

1. **用户明确要求推送后**才执行
2. 提取优化内容关键词（不超过 6 字）
3. 生成标题：`[业务名]+[优化内容]+需求`
4. 首次用 `+create`；**文档已存在时一律 `+update --command overwrite`**——再用 `+create` 会建出重复文档，旧的那份还留在云空间
5. 返回飞书链接

**三条最容易静默出错的**（细节与命令见 `lark-push.md`）：

- **转义**：裸 `<` 写成 `\<`（跳过代码围栏）；**表格单元格开头的 `<` 最危险**
- **附件**：`overwrite` 会清空全部附件，**每次整篇重推后都要重挂**
- **验收**：回读并**逐条比对标题结构**——不要数正文长度，也不要看单次 fetch 的形态

**优化内容提取规则**：
- 从需求背景和功能描述提取核心业务术语
- 优先业务词汇（债务优化、预警管理），避免通用词（系统、管理）

## 原型自检清单

逐条勾，规格全部在 `DESIGN.md`，此处只列检查点：

- [ ] 单文件自包含，双击可直接打开；截图无白屏 / 错位 / 色彩断层
- [ ] **仅亮色**：无 `[data-theme]` 分支、无主题切换；色值与圆角一律走 token，不硬编码十六进制、不自定义圆角 → §2 / §5.1
- [ ] **图标**只用骨架内联 SVG symbol：不混 emoji、外链图标、手写裸 `<svg>`；symbol 内无 `stroke-width` / 端点 / `<g>` → §5.4
- [ ] **一图一义**：菜单项、指标卡、Tab、行操作各横向比一遍，没有两个不同功能共用同一图标 → §5.4
- [ ] **H5 端**用 `.phone` 外壳，375 / 430 宽度下不溢出 → §5.8
- [ ] **Web 端**用 `.web-layout` 外壳，画布锁 1180px；表格横向滚动或加 `.is-fit`，操作列不被截断 → §5.9
- [ ] 每个表单字段有类型与必填标识 → §5.3
- [ ] 空态、加载态、错误态至少各出现一处 → §5.7
- [ ] **数值图表的量程对得上**：每个维度 / 分项的**实测取值范围**与需求里写的范围一致，且**每根条的长度不超过它的分母**（`0 ≤ 值 ÷ 分母 ≤ 1`）。扫描方法：按每题真实量程作答，并把**反向题逐题翻转**，构造「特质最大化 / 最小化」两极各跑一遍——**只按「全选最大 / 全选最小」是测不出来的**：一个维度若有 2 道反向题，选 1 与选 5 的和相同（`1 + (6−1) = 5 + (6−5)`），两极互相抵消、值恒为中间分

## 错误处理

- 输入描述过于模糊：列出 3 个最关键的待确认问题，一次性问清，不猜测推进
- 图片无法识别：说明识别到的部分，请用户补充
- 原型截图异常：检查 HTML 语法与 CSS 变量引用后重试
- 飞书推送异常：**先判别是服务降级还是内容问题**——`+fetch`（读）正常而 `+history-list` / `+update`（写）全超时，即服务端降级，**停下等待，不要反复重试**；其余见 `lark-push.md` §6 与 §7
